# mywiki — Schema & Operating Manual

이 문서는 LLM 에이전트가 **이 위키를 어떻게 운영해야 하는지**를 정의하는 핵심 설정 파일입니다.
LLM은 매 세션 시작 시 이 문서를 읽고, 여기 정의된 규칙·구조·워크플로를 따릅니다.
당신(사용자)과 LLM이 도메인에 맞게 이 문서를 함께 진화시킵니다.

---

## 0. 역할 분담

- **사람**: 소스 큐레이션, 탐색 방향 결정, 좋은 질문 던지기, 의미 해석.
- **LLM**: 그 외 전부 — 읽기, 요약, 교차참조, 페이지 정리(filing), 기록(bookkeeping), 일관성 유지.

LLM은 위키 페이지(`wiki/`)를 **직접 작성·수정**합니다. 사람은 거의 위키를 직접 쓰지 않습니다.
`raw/`는 **절대 수정하지 않습니다**(읽기 전용, 진실의 원천).

---

## 1. 디렉터리 구조

```
mywiki/
├── CLAUDE.md          이 파일 (스키마)
├── README.md          사람용 소개
├── raw/               원본 소스 (immutable)
│   └── assets/        이미지/첨부
└── wiki/              LLM이 소유하는 마크다운
    ├── index.md       내용 카탈로그
    ├── log.md         시간순 기록 (append-only)
    ├── overview.md    전체 개요 / 종합
    ├── entities/      개체 페이지
    ├── concepts/      개념 페이지
    └── sources/       소스별 요약 페이지
```

페이지 종류:
- **source 페이지** (`wiki/sources/`) — `raw/`의 각 소스 1개당 1개. 그 소스가 무엇을 말하는지 요약.
- **entity 페이지** (`wiki/entities/`) — 구체적 대상: 사람, 제품, 조직, 장소, 사건, 데이터셋 등.
- **concept 페이지** (`wiki/concepts/`) — 추상적 대상: 주제, 아이디어, 이론, 방법, 패턴 등.
- **overview.md** — 위키 전체를 관통하는 진화하는 종합(thesis). 새 소스가 들어올 때마다 갱신.

## 2. 페이지 규칙 (conventions)

### 2.1 파일명
- 소문자 + 하이픈(kebab-case). 예: `entities/vannevar-bush.md`, `concepts/retrieval-augmented-generation.md`.
- Obsidian 위키링크는 파일명 기준: `[[vannevar-bush]]`.

### 2.2 Frontmatter (YAML)
모든 위키 페이지 상단에 다음 frontmatter를 둡니다 (Dataview 호환):

```yaml
---
title: 페이지 제목
type: source | entity | concept | overview
created: 2026-05-30
updated: 2026-05-30
tags: [tag1, tag2]
sources: [source-slug-1, source-slug-2]   # 이 페이지가 근거하는 소스들
---
```

source 페이지는 추가로:
```yaml
source_path: raw/원본파일명.md
source_type: article | paper | pdf | transcript | image | data | web
source_date: 2026-05-01      # 원본의 작성/발행일 (알면)
ingested: 2026-05-30
```

### 2.3 본문 구조
- 첫 문단: 1~2문장의 핵심 요약(한 줄 정의).
- 이후 섹션은 `##`로 구분.
- **교차참조는 적극적으로**: 다른 페이지를 언급하면 반드시 `[[위키링크]]`로 연결.
- **주장에는 출처 표기**: `(출처: [[source-slug]])` 형식으로 어떤 소스에서 왔는지 명시.
- **모순 표시**: 새 소스가 기존 주장과 충돌하면 숨기지 말고 명시.
  `> ⚠️ 모순: [[source-a]]는 X라 하지만 [[source-b]]는 Y라 함. (2026-05-30 확인)`

## 3. 운영 ① — INGEST (소스 수집)

소스 투입은 두 가지 방식이 있다 (이 vault의 기본은 **채팅 붙여넣기**):
- **채팅 붙여넣기**: 사용자가 글/메모/파일 내용을 채팅에 붙여넣는다 → LLM이 먼저 `raw/<slug>.md`로 원본을 저장한 뒤(또는 적절한 확장자) ingest를 진행한다. 출처 URL·제목·날짜가 있으면 함께 frontmatter에 기록.
- **파일 투입**: 사용자가 `raw/`에 직접 파일을 넣는다.

사용자가 "ingest 해줘"라고 하면:

1. **읽기/저장**: (채팅 붙여넣기면 먼저 `raw/`에 원본 저장 후) `raw/`의 해당 소스를 읽는다. (이미지 포함 마크다운이면, 먼저 텍스트를 읽고 필요한 이미지는 따로 본다.)
2. **논의**: 핵심 takeaway 3~5개를 사용자와 짧게 공유하고, 강조할 부분을 확인한다.
3. **source 페이지 작성**: `wiki/sources/<slug>.md` 생성. 요약 + 핵심 포인트 + 인용할 만한 부분.
4. **개체/개념 페이지 갱신**: 소스에 등장한 entity·concept에 대해
   - 이미 페이지가 있으면 → 새 정보로 갱신, 교차참조 추가, 모순 점검.
   - 없으면 → 새 페이지 생성.
5. **overview.md 갱신**: 전체 종합에 이 소스가 주는 영향 반영.
6. **index.md 갱신**: 새/변경 페이지를 카탈로그에 반영.
7. **log.md 기록**: 아래 형식으로 항목 추가.

> 한 소스가 보통 10~15개 페이지를 건드립니다. 한 번에 하나씩 수집하며 사용자가 검토하는 것을 기본으로 하되, 배치 수집도 가능.

## 4. 운영 ② — QUERY (질의)

사용자가 위키에 질문하면:

1. **index.md를 먼저 읽어** 관련 페이지 후보를 찾는다.
2. 관련 페이지들을 읽고 **인용과 함께** 답을 종합한다. (검색 도구가 있으면 활용 — §7 참고)
3. 답변 형태는 질문에 맞게: 마크다운 설명, 비교 표, 슬라이드(Marp), 차트(matplotlib), 캔버스 등.
4. **좋은 답은 위키에 보관**: 비교·분석·새로 발견한 연결은 사라지지 않게 새 페이지(보통 `concepts/` 또는 적절한 위치)로 저장하고 index·log 갱신. → 탐색이 누적된다.

---

## 5. 운영 ③ — LINT (건강검진)

"lint 해줘" 또는 주기적으로:

- **모순**: 페이지 간 충돌하는 주장.
- **낡은 주장**: 더 최신 소스가 뒤집은 내용.
- **고아 페이지**: inbound 링크가 없는 페이지.
- **누락 페이지**: 자주 언급되는데 자기 페이지가 없는 개념/개체.
- **누락 교차참조**: 연결되어야 하는데 링크 안 된 페이지.
- **데이터 공백**: 웹 검색으로 메울 수 있는 빈틈 → 새 질문/소스 제안.

결과는 사용자에게 보고하고, log.md에 lint 항목 기록.

## 6. 색인 & 로그 형식

### 6.1 index.md
카테고리(sources / entities / concepts)별로 정리. 각 줄: 링크 + 한 줄 요약 (+ 선택적으로 날짜/소스 수).
**매 ingest마다 갱신.** 질의 시 가장 먼저 읽는 파일.

### 6.2 log.md
Append-only. 각 항목은 **일관된 prefix**로 시작 → unix 도구로 파싱 가능:

```
## [2026-05-30] ingest | <소스 제목>
## [2026-05-30] query  | <질문 요약>
## [2026-05-30] lint   | <점검 결과 요약>
```

`grep "^## \[" wiki/log.md | tail -5` 로 최근 5개 활동 확인 가능.

## 7. 선택: 검색 도구 (CLI)

위키가 커지면(수백 페이지~) index만으로 부족할 수 있음.
- 소규모: index.md + Obsidian 검색으로 충분.
- 중대규모: `qmd`(로컬 BM25/벡터 하이브리드 + LLM 재랭킹, CLI/MCP 제공) 같은 도구를 도입하거나, 간단한 검색 스크립트를 직접 작성.

도구를 추가하면 이 §7에 사용법을 기록한다.
